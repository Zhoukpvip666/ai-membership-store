# T25 — 客户档案与邀请注册重构

**状态：用户已确认业务设计，待实现、审查及独立发布。** 设计基线为已合并 PR #53 的 `main`（`bd9b1168c4fa7acbdaf247f6e9c56cfbf5c61232`）。本文只记录目标行为和验收标准，不代表代码、数据库或线上商城已经更新。现有实现详见 [Task 1.2.2 历史报告](12-authentication-customers-invitations.md) 与 [API 契约](05-api-contract.md)。

## 1. 已确认的业务规则

- 管理员创建的是客户业务档案，不是替客户注册登录身份。创建时仅填写客户备注名称 `adminLabel`，不填写登录邮箱、通知邮箱或密码。
- 客户可先处于待激活状态，管理员仍可为其创建订单及按现有规则关联订阅；登录邮箱不是业务关联的主键。
- 沿用已实现的专属邀请机制与链接格式。邀请链接进入注册流程，客户自行输入邮箱及密码，成功后绑定管理员预先创建的 User，而非新增第二个 User。
- 普通注册与邀请注册共用邮箱规范化、唯一性约束、密码验证、哈希与 Session 逻辑。邮箱已存在时按正常注册规则拒绝，不自动合并账户、不重新归属订单或订阅。
- 邀请注册成功后自动登录。已有账户、订单、订阅、支付记录、历史快照及外键关系不得被重建或重新绑定。
- 迁移时清除真正尚未激活的历史管理员建档客户的预设登录邮箱和通知邮箱；已经激活的用户（包括之后被停用者）完全保留身份及凭证。

## 2. 数据模型及状态约束

继续使用 `User`、`InvitationToken`、`Session`，不新增客户档案表。

| 字段 | 管理员新建档案 | 邀请注册成功后 |
| --- | --- | --- |
| id | 新 UUID | 原 ID，不变 |
| role | CUSTOMER | CUSTOMER，不变 |
| adminLabel | 客户备注名称 | 不变；仅 ADMIN 可见 |
| username | NULL | 保持既有客户自有名称语义 |
| loginEmail | NULL | 客户自行输入的规范化邮箱 |
| notificationEmail | NULL | 按普通注册既有默认规则；未显式设置时保持 NULL，展示可回退至登录邮箱 |
| passwordHash | NULL | Argon2id |
| status | PENDING_ACTIVATION | ACTIVE |
| activatedAt | NULL | 注册成功时间 |
| createdByAdminId / createdAt | 原创建者与创建时间 | 不变 |
| 订单、订阅、历史记录 | 可以已有 | 全部保留 |

将 Prisma `loginEmail` 改为 nullable，保留数据库唯一索引、长度和现有规范化规则。MySQL 允许唯一索引包含多个 NULL；不得使用假邮箱或空字符串代替 NULL。ACTIVE 账户必须拥有非空有效登录邮箱、密码哈希与激活时间；应用层和适当的数据库状态约束共同防止无登录身份的 ACTIVE 账户。DISABLED 状态仍兼容未激活与曾激活两种情况，恢复时根据完整身份状态区分，不得仅凭邮箱推断已激活。

## 3. 注册与邀请契约（目标）

### 管理员创建及管理

- `POST /api/v1/admin/users` 接受严格的 `{adminLabel}`（沿用备注的 1–80 字符规范），返回 HTTP 201 `{user}`，待激活记录的 `loginEmail`、`notificationEmail` 为 NULL。拒绝客户端提供登录邮箱、通知邮箱、密码、角色、状态或其他越权字段。
- 管理员保留备注编辑和现有停用/恢复操作；登录邮箱始终不允许由管理员设置或修改。未领取的档案不预设通知邮箱。已激活客户现有通知联系方式维护规则不因本任务扩大权限。
- 保留 `POST /admin/users/:id/invitations`、`POST /admin/invitations/:id/revoke` 及既有列表/详情 metadata 投影。只为符合未激活条件的 CUSTOMER 签发，7 天有效、成功使用一次；重发撤销旧的未使用令牌，停用撤销未使用令牌。不得返回存量原始令牌、密码或哈希。

### 统一注册

`POST /api/v1/auth/register`：

```ts
interface RegisterRequest {
  email: string
  password: string
  invitationToken?: string
}
```

缺少 invitationToken 时继续现有普通注册：创建新 ACTIVE CUSTOMER 和 Session。有 invitationToken 时验证当前令牌有效性、目标未激活 CUSTOMER 的状态、未绑定登录邮箱及凭证，再原子更新原 User、消费令牌、撤销其余未使用邀请和既有会话、创建新 Session。不能仅凭请求中的 userId 或邮箱认领档案。

邀请注册与普通注册均返回 HTTP 201 `{user}` 和现有安全 Session cookie；保留登录和购买续接、CSRF、角色及归属校验。沿用现有注册限流和统一错误格式：已使用邮箱返回 EMAIL_EXISTS；已登录拒绝注册；过期、撤销、使用过、目标状态不符等邀请返回 INVITATION_INVALID；格式非法按输入校验失败处理。邀请失败不得自动进入普通注册。用户可以修正重复邮箱后再次使用尚有效的邀请。

邀请校验、User 更新、令牌消费、会话撤销/创建必须在同一事务内，保留数据库唯一性约束和并发冲突重试/错误映射。竞争同一个邀请只有一个成功者；两个邀请竞争同一邮箱或普通注册与邀请注册竞争同一邮箱时也只能成功一次，失败的邀请不被消耗。注册与停用、撤销、重发的竞争不得重新启用已停用档案或接受失效令牌。若注册响应丢失，用户可以用已设置邮箱和密码登录。

### 链接与安全

继续使用已经实现的 `APP_BASE_URL/activate#TOKEN` 格式、InvitationToken 哈希存储和复制/撤销方式；不重新设计邀请链接。保留已有 URL 的可达性，入口可复用注册表单与公共注册服务，不暴露两套相互冲突的注册机制。原密码-only 的 `POST /auth/activate` 不得再绕过邮箱绑定与正常注册限制；实现需明确废止或拒绝旧请求，并同步调用方与 API 说明。

令牌仍使用 URL fragment，进入页面后清除当前历史记录中的 fragment，仅在必要的内存状态保留；不得放入查询参数、持久客户端存储、日志或审计。邀请链接是持有者领取档案的凭证，管理员需私下分享给正确对象；本任务不引入邮件验证码、邮箱所有权验证、密码重置或邮件发送服务，不能声称验证了邮箱所有权。注册错误和审计不得泄露档案内的客户备注、订单、订阅或认证秘密。

## 4. 界面与兼容性

- ADMIN 新建客户表单仅保留备注名称；待激活记录显示「待绑定邮箱」，不显示假邮箱。详情继续提供原有邀请生成、复制、撤销、有效期与历史。
- 邀请入口显示登录邮箱、设置密码、确认密码和注册/领取操作；不展示档案内业务数据。成功后进入已登录客户界面，订单与订阅查询仍只基于 Session 所属 User ID。
- 普通注册、客户登录、管理员登录、现有购买续接保持原有规则。邀请失效应明确提示联系管理员，不静默创建另一个账户。
- 通查所有 `loginEmail` 的 Prisma 查询、DTO、前端类型、遮罩、名称回退、搜索、排序、客户选择器、订单和订阅管理。ADMIN 名称依次使用 adminLabel、username、已有邮箱前缀，全部缺失时使用安全且可区分的档案标识。客户投影不泄露 adminLabel；登录成功的身份仍必有邮箱。
- 保持订单与订阅创建所需的独立业务联系字段、冻结快照、权限及金额/履约状态规则；不要为填充联系信息而伪造客户登录邮箱，也不要改写历史快照。

## 5. 迁移与发布边界

- 在现有 14 条迁移之后增加独立版本化 Migration，不改写历史 SQL 或校验和；确认 Prisma schema、数据库约束与实际迁移后的结构一致。
- 先只读分类历史 User：普通已注册/曾激活用户、ADMIN、未激活的管理员建档 CUSTOMER。只清理明确由管理员创建且 `activatedAt IS NULL`、`passwordHash IS NULL` 的真正未激活 CUSTOMER（待激活或从未激活便停用）。清理其 loginEmail 和 notificationEmail，保留状态、ID、备注、关联业务数据与既有邀请。不得修改任何已激活或曾激活用户的邮箱和凭证；对不一致或不明状态先报告，禁止猜测修复。
- MySQL DDL 可能隐式提交：设计并测试失败边界、真实升级路径及重复部署行为，不将 ALTER 和数据清理假设为可整体事务回滚。必须验证 NULL 值与唯一性、历史约束和完整迁移链。
- 同步检查依赖固定 14 条迁移、表/约束数量或 schema fingerprint 的发布、bootstrap、预检、备份/恢复、监控及验收工具。为新版本正确接受新迁移链并保留历史版本与备份兼容边界；不得因本任务关闭完整性检查。
- 开发及所有写入性测试仅使用随机隔离数据库；不连接生产，不迁移或重置现有本地开发库，不覆盖 .env 或数据卷。
- 生产迁移是另一个明确批准的任务。上线前核对目标版本、停止写入/worker、验证可恢复的备份及隔离恢复能力，确认应用与 schema 的兼容性。旧版 API/前端依赖非空邮箱与旧激活语义，不能默认安全回滚；不得在失败后盲目切回旧应用或清空生产库。保留现场并按 [生产部署设计](28-production-deployment-design.md) 处理。

## 6. 验收清单

| 验收 | 通过标准 |
| --- | --- |
| 新建档案 | 多个不同客户可同时无邮箱；只收备注，不允许通过请求写登录身份 |
| 业务关联 | 未领取客户可关联订单、订阅；领取后原 User ID、业务归属与历史数据不变 |
| 普通注册 | 原邮箱规范化、重复检查、会话、角色、购买续接不回归 |
| 邀请注册 | 历史与新生成的既有格式链接可填写邮箱、密码并自动登录，用户仅能读取自己的业务记录 |
| 冲突与失败 | 重复邮箱、错误输入、事务失败不消耗有效邀请；无效邀请不降级 |
| 并发 | 同一邀请及同一邮箱竞争只有一位成功者；重发、撤销、停用与注册竞争安全 |
| 升级 | 从完整上一版本迁移链升级；清理范围准确；已激活及曾激活的停用客户、管理员、令牌与业务记录均按上述规则保留 |
| Fresh install | 新迁移链、首次 ADMIN 初始化、健康检查与相关运维完整性验证适配 |
| 前端 | 桌面、移动创建/领取/登录/选择器及空邮箱展示正常；正常账户与权限边界不回归 |

交付独立实现 PR、准确提交 SHA、相关前后端单测、真实 HTTP + 隔离 MySQL 升级/新装测试、桌面及移动浏览器验收、类型检查、Lint 和构建结果。提交测试命令、实际结果和剩余问题，等待人工审查。设计/实现状态及验收证据由项目文档维护者依据审查结果同步，不能提前标为已完成。

本任务不包括邀请返利、账户合并、邮箱验证、SMTP、支付渠道变更、重新部署服务器或生产上线。
