## 3. Recommended layout

```text
Browser -> https://shop.example.com -> existing host Caddy (80/443)
                                      |-- Vue SPA/static files from a dedicated release
                                      `-- /api and /api/* -> 127.0.0.1:3100
                                                               |
                                                     Node.js 24 / Express
                                                     one dedicated systemd unit
                                                               |
                                             127.0.0.1:3307 -> MySQL 8.4 container:3306
                                                               |
                                                    dedicated persistent volume
```

Use a separate exact-host Caddy site and a project-owned release directory. Keep the API and DB loopback-only. The website and API are same-origin and API requests remain relative. Create a dedicated Unix service identity and install Node 24 at an independent absolute path when approved. Give MySQL a production-specific Compose project, account set and volume. Keep other virtual hosts, the existing port 3000 listener, service units, binaries and data unchanged.

| Option | Trade-off on this host |
| --- | --- |
| **Existing Caddy + systemd API + Docker MySQL** | Reuses the host's TLS listener. The API retains its current loopback binding with a single systemd-managed lifecycle. Node 24 is isolated from Node 22 by its own binary and unit. Requires host service configuration plus Compose, and adds a Docker daemon and MySQL container. |
| **Full Docker Compose** | Repeatable image and private-network lifecycle, but a containerized Caddy cannot take existing ports 80/443. A viable variant retains host Caddy and publishes only the app endpoint to loopback, with MySQL unpublished on the Compose network. This changes API binding and DB-host validation inside the container boundary. It adds packaging and lifecycle work and does not solve the host RAM constraint. |

Prefer the hybrid layout for this shared VPS, conditional on capacity rehearsal. A future container-first operations model can reconsider the full Compose variant.

## 4. Production adaptation

### HTTPS, session and request security

- Introduce explicit production configuration. Require an absolute HTTPS origin with an approved DNS hostname and canonical 443 authority. Reject credentials, IPs, loopback, placeholder domains, unrelated hosts, non-root paths, query strings and fragments. Use the configured origin for invitations and CSRF. Keep the current loopback HTTP/HTTPS development profile and separate staging credentials.
- Add only the new hostname to existing Caddy. Verify DNS A/AAAA, reachability, certificate issue/renewal and HTTP-to-HTTPS redirect. Validate syntax against the installed Caddy version and check Ubuntu security support. Any shared Caddy upgrade/reload requires approval and old-site probes. Keep HTTPS headers scoped to the new site. Test CSP against the actual Vue build before enforcing it. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https)
- Trust only the direct Caddy peer on loopback in the production Express profile, taking account of the actual socket address representation. Leave other proxy trust off. Caddy should disregard Internet-supplied forwarding headers and set canonical forwarding data, preserving the original browser Origin for the CSRF comparison. Never use blanket proxy trust or a raw client-supplied address as the quota key. Dependent local processes belong to the same trust boundary. A CDN needs separate review. [Express proxy trust](https://expressjs.com/en/guide/behind-proxies/), [Caddy forwarding headers](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- Retain current rate limiters and `429` behavior. Test independent clients and prove forged forwarding headers cannot miskey the limiter. Measure catalog, authentication/Argon2 and customer-write traffic, then set ingress quotas and body/time bounds. Account for NAT, map bounds and counters resetting on restart. Use one API instance. Scaling would require shared quotas and a new worker coordination design.
- Preserve `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and no Domain attribute, with matching logout clearing attributes. Preserve the 12-hour hashed Session, revocation, role/ACTIVE checks and ownership isolation. Mutations continue to require exact Origin, `X-Requested-With: MembershipStore` and JSON. Test absent, null and foreign origins. Keep GET/HEAD read-only and avoid CORS exceptions.
- Keep one-time seven-day invitations, manually shared using the approved origin and existing `/activate#…` form. The fragment stays out of HTTP request URLs and [the page](../frontend/src/views/auth/Activate.vue) clears it after capture. Test issuance and activation through Caddy. Revocations or reissues affecting actual users require operator authorization.
- Permit public TCP 80/443 at provider and host firewalls. Keep UDP 443 only under the approved HTTP/3 and existing-site policy. Restrict SSH management paths where feasible with documented recovery access. Keep 2019, 3000, 3100, 3306, 3307, 33060 and dev/upstream ports off the Internet. Check IPv4 and IPv6. Docker publishing must explicitly bind loopback and use a supported security-patched engine. Older Docker releases had a same-L2 localhost publish caveat. [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)

### Build, process, routing and health

- Use a pinned and tested Node 24 LTS patch and npm release on a Linux build host. Use `npm ci` and the checked-in lockfile, generate Prisma Client and build. Package Linux-compatible Prisma/native Argon2 dependencies with the compiled release. Verify the production artifact independently and retain a separate migrator artifact with Prisma CLI, schema and migrations. Keep production secrets out of build inputs, CI logs, static assets and images. Record release SHA, checksums and versions. Review Node advisories, npm full/production dependency trees, Docker base/image and OS/Caddy advisories. Resolve material findings or require explicit risk review. Lockfile updates are reviewed separately and no forced audit fix runs during release. [Node.js releases](https://nodejs.org/en/about/previous-releases), [npm audit](https://docs.npmjs.com/cli/v11/commands/npm-audit/)
- Use an absolute Node 24 binary path and compiled `backend/dist/server.js` in a dedicated non-root systemd unit. Keep release files read-only to the runtime user. Use bounded restart and shutdown policy, journald and an orderly drain. Avoid Vite dev/preview, watch mode, local dotenv fallback, automatic migration and seed in startup. Maintain one unit and two in-process jobs, avoiding concurrent old/new workers during release. Add/test shutdown and maintenance ordering so both job loops quiesce before DB work. Preserve current eligibility and DB-clock behavior on catch-up.
- Reverse proxy exact `/api` and `/api/*` with the prefix preserved, before static routing. For browser page GET/HEAD, serve files or fall back to `index.html`. A missing build asset stays 404. An API error never falls through to SPA HTML. Serve only the dedicated public tree, revalidate HTML, and cache hashed assets. Keep prior assets available for still-open tabs or rollback. Test direct refresh of `/products/:slug`, `/purchase/:slug`, `/account/orders`, `/admin/orders` and `/activate`. [Caddy SPA routing](https://caddyserver.com/docs/caddyfile/patterns#single-page-apps-spas)
- Probe HTTPS page and a real static asset, and independently verify `/api/v1/health` through loopback and intended proxy routing. Keep minimal 200/503 readiness, use process status for liveness and avoid restart loops for a transient DB problem. Verify schema/triggers independently from readiness. Track last successful sweep and lag for each job in operator metrics. Use explicit 503 maintenance responses when traffic is gated.

### Credentials, logs and data

- Require a dedicated production schema and MySQL volume. Validate runtime `DATABASE_URL` as MySQL with the approved loopback host, port/schema and properly encoded credentials. Reject dev/test/placeholder credentials. Use a least-privilege runtime account, a separate migrator/trigger-definer, scoped backup/restore credentials and DBA access. Keep root, migrator and bootstrap credentials outside the API environment. Use protected secret files or a systemd credential adapter outside the repo. Rotate credentials and retain backup-key custody under operator procedures. [systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
- Use structured logs with UTC time, release ID, server-generated request ID, route template/class, status and duration. Keep business audit records separate. Omit request/response bodies, full queries, cookies, authorization/sign-in data, idempotency keys, invitation links, form values, payment credentials, driver error detail, URLs with secrets and process env. Drop sensitive headers and query fields from Caddy access logs. If the installed Caddy version cannot safely filter them, use a verified safe logging path before enabling access logs. [Caddy log controls](https://caddyserver.com/docs/caddyfile/directives/log)
- Bound journald retention/disk usage and configure Caddy/MySQL log rotation. Verify redaction with synthetic markers. Alert on TLS/health, latency and 5xx, restarts/OOM, swap, disk/inodes, backup age/failure, worker lag and other-site degradation. Review operator access, retention and data-request handling. Preserve immutable order history and audit trails. [journald retention](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html)

## 5. Database lifecycle and recovery

1. **Prepare the target.** Pin a tested MySQL 8.4 patch/digest and use a dedicated volume with UTC, checked resource limits and no public DB publishing. Budget for redo/binlogs, data, backups and a separate restore. Before an approved release, verify version/charset/collation/SQL mode, binlogging, grants, schema, counts, migrations and trigger state. Leave existing application stores outside this target.
2. **Take and verify a backup.** For an upgrade, gate traffic and quiesce writers before the backup. Use a MySQL 8.4 logical dump with `--single-transaction --quick --skip-lock-tables --triggers --no-tablespaces` appropriate to the tested InnoDB setup. Rehearse permissions and GTID behavior and avoid concurrent DDL. Include tables/data, migration records, triggers and any applicable stored objects. Keep protected provisioning metadata for grants and definers. Check exit status, completeness, nonzero size and checksum. Encrypt and retain copies off-host and test a restore into an isolated target. Use a restricted credentials file or equivalent. Agree backup frequency, retention and RPO/RTO. If point-in-time recovery is required, design and rehearse binlog preservation and replay. [MySQL mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)
3. **Rehearse migrations.** Exercise both a fresh database and supported historical upgrade with synthetic data. The baseline has 12 committed migrations. [The migration wrapper](../backend/scripts/prisma.ts) checks for historical SUSPENDED subscriptions via [migration preflight](../backend/src/db/migration-preflight.ts). [Migration ten](../backend/prisma/migrations/20261118050000_order_source_final/migration.sql) rejects retired/invalid order sources. Report incompatibilities without repairing or cleaning live data. Compare checksums, migration tracking, schema, CHECKs, FKs and trigger definers/execution ordering.
4. **Apply only under separate approval.** Verify the backup and stop all writers and workers. Use one Prisma `migrate deploy` operation through the reviewed wrapper and scoped deployment identity, with advisory locking retained. Keep historical SQL unchanged. Trigger creation needs `TRIGGER` and can require separate DBA action with binlog enabled. The implicit DEFINER is the migration account. Preserve that identity and its activation-time permissions, including required table reads. Do not give global/DDL rights to the application. Any temporary grants or `log_bin_trust_function_creators` change need their own approval and a verified before/after restoration plan. Check schema drift and custom SQL objects separately and verify no pending migrations. [Prisma migrate deploy](https://docs.prisma.io/docs/cli/migrate/deploy), [MySQL triggers](https://dev.mysql.com/doc/refman/8.4/en/create-trigger.html), [MySQL binlog restrictions](https://dev.mysql.com/doc/refman/8.4/en/stored-programs-logging.html)
5. **Bootstrap explicitly on a new target.** [Existing bootstrap](../backend/src/db/seed.ts) creates the expected administrator and AppSettings idempotently and detects collisions. Run it only after approval with a one-time credential context. Confirm the administrator and settings, then remove bootstrap credentials from the runtime context. Validate time zone, catalog availability and plain-text payment instructions. A populated database is not a seed target.
6. **Separate artifact rollback from schema recovery.** If schema compatibility is proven, keep traffic gated, stop the new API/workers, switch together to the prior verified frontend/API artifacts, and verify health before reopening. With partial migration or unknown compatibility, stay in maintenance. Individual MySQL DDL statements can have committed. Inspect tracking and actual objects read-only, then agree recovery with the DBA. No blind retry, `migrate resolve`, `migrate reset`, `db push` or replacing the source volume.
7. **Restore to a separate destination.** Preserve the failed volume and verify recovered versions, grants, triggers, counts, order/payment/refund/subscription history and idempotency records. If restoring an earlier point discards writes, reconcile offline payments/refunds and affected orders before enabling writes. Address restored sessions/invitations that may otherwise become valid again after revocation. Cut over only with separate approval and repeat app, worker and existing-site probes.

## 7. T23.5 controlled production launch

This is the production runbook outline. Start with accepted T23.1–T23.4 results and separate approval of the exact release, host, database, domain, window, responsible operators, permitted operations and rollback thresholds. Design review, rehearsal and the decision to keep three services stopped are not production change approvals.

1. **Preflight and rollback baseline.** Verify artifact SHA/checksums, dependency versions, capacity evidence, available disk, listener conflicts, current service and boot states, and operator access. Record read-only status, TLS and latency probes for each existing site and save the approved rollback artifacts and previous scoped DNS, firewall, Caddy and unit settings. Preserve other virtual hosts and the current SSH recovery path. Defer if an existing site is unhealthy or the host has drifted outside the approved plan.
2. **Gate writes and verify a recovery point.** Keep the new site in maintenance and quiesce all application writers and workers before a coordinated backup or schema change. Verify the dedicated MySQL instance is reachable on loopback, starting its approved Compose project if required and separately authorized. For an existing target, take the separately approved encrypted backup and verify its checksum, off-host availability and isolated restore evidence against Section 5. For a fresh target, verify its identity and emptiness, document its initial state and confirm a recovery path that leaves existing databases and volumes untouched. Treat absent or unverified recovery evidence as a stop condition.
3. **Apply the approved Migration.** Run only the explicitly approved Prisma migration batch with the dedicated identity and advisory lock. Verify migration history, schema, triggers and grants before service start. Bootstrap a new database only under its own approval. If any step fails, keep maintenance active, preserve data and inspect what committed. Escalate to the DBA before retrying, restoring or changing the migration state.
4. **Start the API and prepare ingress.** Start the dedicated API unit after schema verification and under separate approval. Check loopback bindings, readiness and exactly one API/worker instance. Separately approve and verify any DNS A/AAAA and firewall changes, including management access and private ports. Validate the prospective Caddy configuration, scope it to the new hostname and keep a maintenance or restricted smoke-test gate while obtaining TLS. Reload Caddy only with explicit approval and check existing sites immediately afterward.
5. **Smoke test and open traffic.** From authorized clients verify HTTPS, the SPA and an actual static asset, API readiness, JSON API errors, login/logout, origin enforcement, roles and order ownership. Check worker health, logs and resource use. Use read-only production probes by default. Any smoke test that writes needs its own approved identity, data and cleanup plan. Compare existing-site TLS/status/latency with the baseline. Obtain go/no-go sign-off before opening customer traffic, then monitor the new and existing sites through the agreed observation window.
6. **Rollback on failure.** On TLS/routing failures, readiness failures, existing-site regressions or a breached capacity threshold, gate the new site and pause its writers/workers. Under separately authorized rollback steps, revert scoped DNS/firewall/Caddy changes and reload Caddy when required. Restore the prior app/unit/artifacts only with proven schema compatibility. For partial DDL or unverified compatibility, keep writes closed and follow the separately approved recovery and reconciliation in Section 5. Recheck existing sites and management access, verify the recovered state and obtain sign-off before reopening. Record what changed and account for cached DNS during recovery.
