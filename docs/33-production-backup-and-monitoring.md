# T23.3 production backup, restore and monitoring

T23.1 and T23.2 are merged through [PR #51](https://github.com/lear111/ai-membership-store/pull/51). T23.3 supplies repository templates and a synthetic recovery rehearsal. Capacity, credentials, real offsite storage, live install and rollout remain approved operations in T23.4 and T23.5. See the [controlled rollout plan](28-production-deployment-design.md).

## Prepare the dedicated target

Use the approved Ubuntu 24.04 amd64 host, MySQL 8.4.13 pinned in Compose and the single API service from [the infrastructure runbook](32-production-infrastructure.md). Keep the existing host uses and Caddy global configuration intact. The historical 2 GiB inventory does not establish time or memory during backup traffic. Run jobs at lower CPU/IO priority and measure coexisting-site latency, memory, disk and backup duration before rollout.

1. In the approved host window, place the reviewed `deploy` tree in the root-owned operations directory `/opt/ai-membership-store/ops/deploy`. Use root:root 0600 for `/etc/ai-membership-store/{ops.json,backup.env,backup.mysql.cnf,restic-password}` and the optional `monitor.env`. The ops units are root-only for local Docker socket, journald and image access. The API account receives no credential files or Docker access. Preserve the existing image ownership/modes.
2. Download `restic_0.20.0_linux_amd64.bz2`, `SHA256SUMS` and `SHA256SUMS.asc` from the official release. Obtain `gpg-key-alex.asc` from the official installation guide. In a new private staging directory run `bash deploy/ops/verify-restic.sh DOWNLOAD_DIR NEW_BINARY`. It verifies the signed checksum list against the full pinned signer fingerprint, checks the archive checksum, decompresses and checks the Linux amd64 version. Install the verified binary as root:root 0555 at `/opt/restic-0.20.0/restic` under a root-owned 0755 version directory. Review and retest before switching the fixed version. [Restic installation and signing key](https://restic.readthedocs.io/en/stable/020_installation.html#stable-releases), [official 0.20.0 release](https://github.com/restic/restic/releases/tag/v0.20.0)
3. Render both MySQL Compose files together. On a fresh approved production instance, use `compose.yaml` with `backup.compose.yaml` to provision the dedicated internal backup network with the database. The backup helper runs a short-lived client on that network with no ports and a read-only MySQL options file. If attaching the overlay would recreate an already-running server, schedule that separately. The primary publication remains loopback only.
4. As DBA, check all schema objects with full metadata visibility before authorizing this backup profile and after every DDL change. Compare the 14 applied migration names and checksums with the reviewed operations release. Enumerate engine, views, routines, events, triggers, their definers/order and required grants. The automated check also compares visible metadata before/after backup, rejects non-InnoDB tables, visible unsupported objects, missing triggers and an incomplete migration chain. A least-privilege backup login may not see every routine or event. A DBA finding of any view, routine, event or non-InnoDB object requires a separate consistency and grant review before use.
5. Create `membership_backup` scoped to the approved backup-network address range and this schema. Grant SELECT and TRIGGER on exactly `membership_production`. Verify client TLS and the expected login with `CURRENT_USER()` and `SHOW GRANTS`. The TRIGGER grant exposes trigger definitions and has DDL implications. Keep that identity private, omit all business write, global/administrative and definer grants, and preserve the reviewed binlog restrictions. The isolated fixture proves UPDATE is denied. Use the separate T23.1 migrator identity for DDL and the stored trigger definer. [MySQL mysqldump privileges and options](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

## Initialize an offsite encrypted repository

Select and approve a different host or HTTPS S3-compatible storage endpoint. Record its identity and the storage operator. The production helper accepts `sftp:membership-offsite:/approved/repository` or `s3:https://HOST/BUCKET/PREFIX` and checks for local/loopback endpoints. For SFTP provision the dedicated SSH config, private key and independently verified known_hosts as root:root 0600. Use the exact alias and strict host-key checking. For S3 use scoped access to this prefix with TLS and a separate root:root 0600 shared AWS credential file. Configure backup and separately approved deletion privileges with the storage owner. Do not put secrets or token-bearing endpoints in Git, commands, build inputs or logs.

Fill `backup.env` from the example with `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` and, for S3, `AWS_SHARED_CREDENTIALS_FILE`. Recoverability requires preserving the Restic password, repository access and the verified host key or CA in the approved off-host credential store. The public storage host is independently vetted as offsite. Synthetic tests may use the explicitly isolated local fixture mode only.

After approval, use the private environment through systemd to invoke `python3 -B deploy/ops/backup.py init` once. For manual operator commands use a root shell with the approved backup context loaded through a protected environment-file runner, not a pasted password or interactive command containing secrets. The scheduled unit uses `EnvironmentFile` and normal execution starts with `backup`. Start the timer only after a manually verified first backup and check.

## Run, verify and retain paired backups

- The database snapshot uses Restic `backup --stdin-from-command` with the pinned MySQL client. The dump uses `--single-transaction --quick --skip-lock-tables --triggers --no-tablespaces --set-gtid-purged=OFF --hex-blob --default-character-set=utf8mb4 --skip-add-drop-table`. Failure from mysqldump invalidates the snapshot. No SQL staging file is held on disk.
- A repository lock serializes backup, check, retention and restore commands on this host. Run only one backup coordinator per dedicated repository. Database snapshot comes first, then both image directories. Image writes publish immutable names before database references commit. Freeze image deletion and schema changes for the entire interval. A file snapshot can contain harmless extra files. All image references present in the database snapshot must still exist by the later file snapshot. Keep that write ordering and cleanup freeze even when adding a new image implementation.
- An encrypted third snapshot holds the completion manifest with the run ID, two snapshot IDs, release SHA, schema fingerprint, MySQL version, migration names/checksums and trigger definer identities. The local lock-protected success state updates only after all three snapshots succeed. Partial snapshots are retained for diagnosis and lack the completion marker. Use `backup.py inspect --run RUN_ID` to check the protected manifest without dumping business content.
- Daily `backup.py check` verifies repository metadata and all completion manifests. Weekly `backup.py check-data` reads all encrypted packs to verify integrity. Adjust the timers based on measured duration and existing-site impact. Inspect a failed check before retrying. Preserve available packs and known-good completed runs. Investigate storage, network, credentials, keys and manifests. Restore a known-good set into a separate environment to validate recovery. Repair, deletion and alternate recovery choices require independent authorization.
- `backup.py plan-retention` is the dry run before `apply-retention`. The policy retains the newest complete run in 24 populated UTC hour windows, 14 UTC day windows, 8 ISO weeks and 12 months, plus the latest complete run. The windows combine by union. Adjust `keepHourly`, `keepDaily`, `keepWeekly`, `keepMonthly` and `incompleteDays` in `ops.json`. Partial groups wait at least the configured grace (default 7 days). Failure during removal cannot leave a marker referring to intentionally forgotten data because the marker is forgotten first. Run `plan-prune` to estimate reclaim and review `prune` under separate approval. Both require a healthy repository with a complete run. No timer performs retention deletion or prune.

The backup timer defaults to 00:00, 06:00, 12:00 and 18:00 UTC. Change its calendar using an approved unit drop-in. Suggested RPO ≤6 hours and RTO ≤4 hours are objectives. Measure effective RPO from the recovered transaction cutoff relative to incident time, including failed/delayed runs. The manifest records when the database snapshot command started, a conservative lower bound on that cutoff. Measure RTO from incident declaration through target initialization, encrypted download, import, verification, reconciliation and usable API recovery. A six-hour schedule does not prove a six-hour RPO.

## Recover to a fresh isolated MySQL instance

1. Gate production traffic and preserve the source database, repository and any failure artifacts. Approve a new disposable project name `membership-restore-<12 lowercase hexadecimal digits>`, a private internal network and a new volume as defined by [restore.compose.yaml](../deploy/mysql/restore.compose.yaml). Provide different synthetic root/password and socket client option files via `RESTORE_ROOT_FILE` and `RESTORE_CLIENT_FILE`. Use Compose with an explicit project name and explicit empty environment file. Check the project and volume identity before starting. The helper accepts a local Docker socket and that exact isolated project layout. It rejects exposed ports, unexpected mounts, an unexpected image or a nonempty target database.
2. Inspect the encrypted manifest for the approved run. Provision the necessary definer identities and minimum grants on the isolated instance before import. Recreate the scoped application login separately. Do not copy any MySQL system schemas, password, user table from the system database, or root grant. The restore helper checks declared definer identities before writing. Review MySQL's DDL/binlog requirements with the DBA for this isolated target.
3. Run `python3 -B deploy/ops/backup.py restore --run RUN_ID --project PROJECT --output /private/PROJECT-images` in the approved credentials context. Choose a new path named for the project. The helper verifies the file snapshot, streams the SQL into the verified socket-only target, and compares schema fingerprint, all migration names/checksums, Trigger definitions/order/definers, indexes, CHECKs and foreign keys. It checks product and QR references against the restored paired directories. The command records elapsed restore time. Retain the private restore directories for acceptance until explicitly safe to remove.
4. Compare per-table counts with a consistent source record when available. Verify both images and start the isolated API against the restored instance with scoped credentials and storage directories. Test administrator and customer sign-in, public catalog, owned order and protected image reads. For production recovery, reconcile external payment/refund events and review restored sessions/invitations before cutover. A failed restore can leave a partial isolated instance or files. Keep the source backup intact, inspect failure state and use another fresh target for an approved retry. Never retry over a partial target or point this tool at the original.

The [synthetic rehearsal](../deploy/ops/test/rehearse.sh) uses random project names, versions the target separately, initializes a temporary encrypted repository, restores it and exercises the API. It requires the verified Restic binary, the prior Linux operations archive built with the same lockfile and a checkout with freshly built `backend/dist`. Run on Linux with local Docker as a root fixture operator. Only the disposable fixture projects are stopped/cleaned after success. An unsuccessful fixture keeps its files for diagnosis. The runner compares SQL counts and byte-identical images before API sign-in creates new sessions.

## Private logs and alert triage

Apply the namespace-specific journald drop-in under `/etc/systemd/journald@ai-membership-store.conf.d/` in the authorized rollout. The API and ops units emit UTC JSON under `LogNamespace=ai-membership-store`. The profile requests 14-day maximum retention and approximately 100 MiB. Inspect with `journalctl --namespace=ai-membership-store -u ai-membership-store.service --since today -o cat` and `journalctl --namespace=ai-membership-store --disk-usage`. MySQL uses the Compose json-file driver with 10 MiB × 3 rotation. Verify daemon settings on the dedicated project. Caddy's existing global logging is outside this change. The site template returns 404 for `/internal` and `/internal/*`.

The API writes fixed classes and error codes, UUID request IDs, methods, statuses, durations, worker outcomes and the installed release SHA. `/internal/ops/metrics` uses the actual loopback peer, without trusting forwarded headers, and is outside the public proxy. Workers expose bounded start/success/completion timestamps, duration, failure run length, currently running state and a full-batch backlog signal. The five-minute request histogram stores no URLs or identities. Request p95 is a bucket estimate. Synthetic tests verify private payloads and driver errors remain out of the logs.

The minute monitor checks API systemd state, actual DB readiness via health, latency/5xx, the MySQL container, both workers, CPU/load/memory/swap, disk and inodes, last complete backup, repository check age, journal size, restarts/OOM, public TLS expiry and configured existing-site probes. Configure approved HTTPS origins, site URLs and thresholds in `ops.json`. Site alerts report position in that list, without copying the URL. Private local state and logs identify the failing check. On resource pressure, check active workers, filesystem growth, backup windows and other workloads before changing settings. On stale or failed backup, check both manifests and the recovery point. Inspect the API and namespace logs for an availability or worker alarm.

Set optional `ALERT_WEBHOOK_URL` via `monitor.env`. It uses HTTPS JSON with a strict timeout, no redirect following and cooldown per fault. Each check attempts at most six deliveries, prioritizing alerts that have waited longest. Failed deliveries are logged with a generic code and retried with a bounded delay. An accepted failure notification is followed by a recovery notification when the condition clears. Without a webhook, transitions remain available in the local namespace. The on-failure unit triggers and timers provide local diagnostics even when the webhook is unavailable.

## Validation boundary

The commands for this stage include Bash syntax checks, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, `npm run build`, the Python operations tests, Compose rendering, `systemd-analyze verify` and the isolated rehearsal. Test reports in the PR identify the exact commit, measured data and any environmental limitations. The synthetic repository verifies Restic encryption and recovery. The real remote backend, shared-host system service behavior, and capacity/RPO/RTO acceptance remain T23.4 gates.
